## 1. 只读分析结论

- 身份即边界：`createRunContext` 产出 deep-frozen 对象，训练态固定 `Training_Materials/runs/<runId>` 且 `releaseId/projectId` 为 null；交付态固定 `team/artifacts/<runId>` 且 pin `releaseId/projectId`（`profileSource`/`orchestrationSource` 直接指向对应 release 目录）。训练态显式拒绝绑定 `releaseId`。
- 写权限：`runWriteDecision` 只能拒绝（deny-only）。release 快照（`team/ptc/releases` 与任意 `/versions/` 段）对两种模式一律不可写；训练态只能写自身 run 根，交付态只能写 `project/<projectId>` 或自身 artifacts 根。
- 持久化：`persistRunContext` 原子写（tmp + rename + `wx`），已存在且内容不同则 throw，相同则幂等。
- 训练编排：`createTrainingRun` 在写任何文件**之前**完成 target 校验（未知 profile、乱序 pipeline 均在创建目录前失败）。
- 完整性：release 目录按 `localeCompare('en')` 排序逐文件精确字节 SHA-256，symlink 直接 throw；`verifyReleaseDirectory` 先做 manifest 结构校验（排序唯一、路径合法、size/sha 格式），再逐项对比并校验 `bundleDigest`。

## 4. 发现的真实实现缺口（未改实现、未伪装为通过）

- **G1 训练态静默丢弃 `projectId`**：`createRunContext` 对 training 模式仅拒绝 `releaseId`，传入的 `projectId` 被无声丢弃（输出恒为 null）。测试以特征化断言记录（`mode confusion` 用例中 `pattern: null` 分支）。属于对称性缺口，是否收紧需实现方决策。
- **G2 runId 命名空间按模式分裂**：同一 `runId` 可同时持有训练身份（`Training_Materials/runs/<id>/run.json`）与交付身份（`team/artifacts/<id>/run.json`），`persistRunContext` 无法察觉该碰撞。测试以特征化断言记录（`immutable run.json` 用例 modeSwap 分支）。若审计/账目要求 runId 全局唯一，此为缺口。
- **G3 walker 与校验器排序规则不一致（生产者自产 manifest 被自家校验器拒绝）**：`walk()` 按 `localeCompare(name, 'en')` 排序，`validateExpected` 按码点序比较。含混大小写文件名（如 `a.txt` 与 `B.txt`）时 `buildReleaseFileEntries` + `digestReleaseEntries` 产出的 manifest，喂回 `verifyReleaseDirectory` 会抛 `release manifest files must be unique and sorted`。本机构建（full-ICU）已复现并以 `documents locale-vs-codepoint ordering divergence` 用例钉住。真实缺陷，修复需统一两侧排序规则（超出本任务白名单）。
- **G4 symlink 端到端未在本机跑通**：Windows 无开发者模式/管理员权限时 `fs.symlinkSync` 抛 EPERM，walker 的 `isSymbolicLink` throw 守护未被执行验证（用例降级为 diagnostic；既有 `release-integrity.test.mjs` 存在同样局限）。需在具备权限的环境补跑，或改用 junction/目录遍历等替代路径验证。
- **G5（范围说明，非缺陷）**：`runWriteDecision` 是纯决策函数，返回建议而非强制；实际写入无 lib 层拦截器强制执行该决策（模块注释自述 deny-only、角色级守卫在后）。真实写入强制的存在性无法仅凭这三个模块的公开接口断言，超出本次白名单，留待专项验证。
