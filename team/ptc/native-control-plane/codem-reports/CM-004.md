## 3. Schema 字段（冻结 v1）

顶层对象 `additionalProperties: false`，必填字段如下：

| 字段 | 类型 / 规则 | 说明 |
|---|---|---|
| `schemaVersion` | `const 1` | 契约版本；任何变化必须升版本 |
| `releaseId` | string，`^[A-Za-z0-9][A-Za-z0-9._-]*$`，非空 | 与发布目录名一致，如 `ptc-release-v1` |
| `createdAt` | string，`format: date-time` | RFC 3339 发布时间 |
| `createdBy` | string，非空 | 发布者 |
| `previousReleaseId` | string（同 releaseId 规则）或 `null` | 回退指针；首版为 null |
| `snapshots` | object，五键必填，`additionalProperties: false` | `profiles` / `orchestration` / `contracts` / `policies` / `verification`，每类为非空、去重的 path 数组，且逐类用 `pattern: "^<category>/"` 强制路径前缀 |
| `files` | array，`minItems 1`、`uniqueItems`（整项） | 详见下 |
| `bundleDigest` | string，`^[a-f0-9]{64}$` | files 规范列表的小写 64 位 SHA-256 |
| `releaseVerification` | object，三键必填，`additionalProperties: false` | `result` / `singleAgentEvaluation` / `pipelineRegression`，各为 enum `["passed","failed"]` |

`files[]` 条目：`additionalProperties: false`，必填 `path` / `size` / `sha256`：

- `path`：非空；`pattern: "^[^\\\\/]"` 拒绝首字符为 `/` 或 `\`；`not anyOf` 拒绝任意反斜杠（`\\`）与 `..` 段（`(^|/)\.\.(/|$)`）——与 lib 的 `validateExpected` 路径规则逐条对齐。
- `size`：integer，`0 ≤ size ≤ 9007199254740991`（Number.MAX_SAFE_INTEGER，对应 lib 的 `Number.isSafeInteger`）。
- `sha256`：`^[a-f0-9]{64}$`，小写十六进制。
- `files` 整体用 `not contains (path const "release-manifest.json")` 禁止 manifest 把自己列入清单（与 lib walker 过滤根 manifest 的行为对齐）。

Schema 内无法表达、由测试补足的语义规则见第 4 节；schema 与测试合起来才构成完整契约。

## 4. 无法由 JSON Schema 表达、由测试补足的语义检查

测试中的 `semanticErrors()` 返回稳定错误码，逐条对应冻结接口要求：

| 码 | 规则 | 依据 |
|---|---|---|
| `files-not-sorted-unique` | files 按 path 严格升序（从而按 path 唯一）；比较用 JS 字符串比较（UTF-16 code unit），与 lib `entry.path <= previous` 完全一致。schema 的 `uniqueItems` 只能保证整项相等去重，不能保证 path 键唯一 | 任务冻结接口 + lib `validateExpected` |
| `bundle-digest-mismatch` | `bundleDigest` 必须等于 `digestReleaseEntries(files)`（测试直接调用 lib 复算） | 哈希合同：确定性生产者拥有哈希计算 |
| `snapshot-path-not-in-files` | snapshots 声明的每个 path 必须存在于 files | 五类快照声明必须落在实际文件上 |
| `file-not-declared-in-snapshots` | files 中每个 path 必须被某一类快照声明（并集相等；跨类重复被 schema 的类别前缀模式排除） | 计划 5.4：发布包内容 = 五类快照 |
| `release-verification-inconsistent` | `result: "passed"` 要求两个子结论同时 `passed` | 计划第 6 节/阶段 5：评估与回归全过才可发布 |
| `previous-release-id-self` | `previousReleaseId` 非 null 时必须 ≠ `releaseId` | 回退指针语义 |

另有一个对齐性测试（非夹具驱动）：将有效夹具的 files 反序后，本测试的语义检查与 lib 的 `verifyReleaseDirectory` 抛出的 `/unique and sorted/` 同时命中；有效夹具条目能通过 lib 的 `validateExpected`（在缺失目录上报 ENOENT 而非校验失败），证明两边排序/路径规则完全一致。

## 6. 设计决策

1. `snapshots.<category>` 直接是 path 字符串数组（不带元数据包装）：文件哈希/大小已在 `files[]` 中，按 `profiles/<profileId>/` 前缀可推导 profileId；保持 v1 最小。
2. 每类快照 `minItems: 1`：五类中任一类为空的发布包按 fail-closed 拒绝。
3. `releaseVerification` 用 enum `passed/failed` 而非 boolean，为后续结论细分留空间；schema 允许 `failed` 文档存在（记录失败证据），但语义规则保证 `passed` 的一致性——"failed 的 manifest 不得激活"属激活面（active-release 指针）职责，不在本 schema 范围。
4. `$id` 使用保留域 `https://dsh-ptc.invalid/schemas/release-manifest-1.schema.json`，避免暗示真实网络位置。
5. 测试内嵌校验器对 `format: date-time` 启用断言（draft 2020-12 默认 format 仅注解）；见未决问题 3。

## 7. 未决问题（需 Codex 集成时裁决）

1. **`releaseId` 是否钉死为 `^ptc-release-v\d+$`**：当前用宽松的 `^[A-Za-z0-9][A-Za-z0-9._-]*$`（兼容计划中 `ptc-release-vN` 目录名但不强制）。若目录名即 releaseId 是硬约束，可收紧 pattern。
2. **每 Agent 显式元数据**：计划第 6 节要求固定"每个 Agent 的 profileId、版本和文件哈希"。当前 v1 由 `profiles/<profileId>/` 路径 + `files[]` 哈希隐式覆盖；若需要显式 `profiles: [{profileId, version, files}]` 结构，属 schemaVersion 2 变更。
3. **format 断言的消费端责任**：`createdAt` 的 date-time 约束在 2020-12 中默认不生效；本测试内嵌校验器已断言它，但若 Codex 侧用 Ajv 等标准校验器消费 schema，需自行开启 format 断言（如 `ajv-formats`）。
4. **测试未接入 `all.test.mjs`**：按任务约束未修改 `all.test.mjs`；是否将 `release-manifest-schema.test.mjs` 加入聚合入口由 Codex 决定（当前用独立命令运行）。
5. **`releaseVerification` 结论与 `verification/` 证据文件的绑定**：当前结论与证据文件仅通过类目前缀共存于一个 manifest，schema 不校验"结论与证据内容一致"（证据文件内容是发布流程私有格式）；若需要强绑定，应在其 JSON Schema 中定义，属后续任务。
