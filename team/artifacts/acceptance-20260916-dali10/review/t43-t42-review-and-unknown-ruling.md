## 1. 我独立复现 t42 的核心前提 —— **成立，且我找到比它更强的证据**
**(a) 站点绑定宏给出该仪器的完整通道清单（24 条）**：`Pin_Channel_define.h:62`
`_PIN_SITE_BIND_DEFINE_MD_ACM200_SITE1_ = "S5_0,S5_1,…,S5_23"`。
**(b) `_GROUP_CHANNEL_DEFINE_ACM_GRP_`（L57，全文 192 token）我逐 token 解析**：其第二 token 的**取值集合恰为 `{0,1,…,23}`（24 个通道索引）**、且同一站点固定为 S5/S6/S11/S12/S21/S22/S27/S28 ⇒ **该宏是"24 条通道 × 8 站点"的并集**。
**(c) 24 个 `_PIN_CHANNEL_DEFINE_*_ACM_` 宏占 `:15-38`，索引严格 0..23**（我逐条列过）。
⇒ **`_5` 是通道索引，证据强。** 另：`knowledge/sources/hardware-specs.md` 的 ACM200 = **24 通道** 与之自洽。

## 2. 但 t42 的**第二步**存在**未解释的直接反证** —— 契约逐字写的是 `S5_FH18`
`setup-contract.json` → `aliasResolution[3].resolution.relayChain`（**逐字，我读过原文**）：
```
{ "relay": "K110_ACM18_BST", "number": 110, "state": "SetOn (ACM200 S5_FH18 -> BST)" }
{ "relay": "K61_ACM8_SW",    "number": 61,  "state": "SetOn (ACM200 S5_FH8  -> SW)"  }
```
**契约不是"只给了继电器号"，它给了**引脚名**（`S5_FH18` / `S5_FH8`）。** 而 t42 主张该路线属"通道 18 的另一个仪器对象 `PB0_BST_ACM`" —— 那么契约为何在同一 `relayChain` 里用 `SW12_U1REF_BST_ACM` 之名配 `FH18`？**t42 把它归为"契约错误/需要改名"，但未提供任何独立证据证明契约"本意是 ch5"**；其 §4 表格只是把与它结论不符的字段一律标 `✘`（`resources[2].channelsInScope.BST`、`relayChain[0]`、`aliasFlatTable[3].relayPath`），**这是"以结论判证据"，不是"以证据判契约"**。
**⇒ 因此 t42 的第 2、3 步（"故 `[48,76]` 必需、K110 非必需"）我**不予背书**；其第 1 步（通道索引）我采纳。**

## 3. 我补一条 t42 未处理的**强反证**（网表，FACT）
我实测 `Dali-SCH.csv` 的 net 成员：
```
S5_ACM200_FH5   ∈ NetK46_BUS_FH_SW1_S1_2  = K46.2 + K48.6         → 通道 5 落 K48 → K76 → BST
S5_ACM200_FH8   ∈ NetK60_BUSL_VCP_S1_4    = K60.4 + K61.6         → 通道 8 落 K60/K61 → SW
S5_ACM200_FH18  ∈ NetK109_BUSL_PB0_S1_4   = K109.4 + K110.6       → 通道 18 落 K109/K110 → PB0/BST
```
⇒ **三条通道各走各的继电器，互不重叠**。**契约 `relayChain` 逐字采用的是通道 18 与通道 8；t42 认为应采用通道 5 与通道 8。**
**两者不可能同时为真**，而**两者都能解释"实现为何能跑通"**：若按契约（ch18+ch8），`K110`+`K61` 正确；若按 t42（ch5+ch8），则 SW 侧仍用 **ch8**（`K61`）—— **注意 t42 自己也保留 `K61`（ch8）作为 SW 端** ⇒ **它的方案同样混用了两个通道**，这削弱了"一个仪器只有一个通道"的推论。**

## 4. UNKNOWN 裁定 + 可执行的**最小修法**（落盘前）
**裁定：TM600 是否须由 ch5 驱动 BST —— 属 UNKNOWN，须 `t42` 与契约 owner/机台证据裁定。**
**在裁定前，我给出**唯一对两种裁定都安全**的最小修法**：
> **在 `TM600_HS_RDSON` 的 `SetOn` 中**同时**闭合通道 5 的 BST 支路与契约字面要求的支路** —— 即**在现有 9 项之外追加 `K48_AMP_REF` + `K76_ACM_BST`**（现有已含 `K109_K110`、`K61`、`K60`）。
**判据（为何这是唯一安全解）**：
- **若 ch5 成立**：不补 `K48/K76` ⇒ **BST 不可达**（真缺陷，见 §3 网表）⇒ 必须补；
- **若 ch18 成立**（契约字面）：补 `K48/K76` 只是**并入另一条已存在的 BST 并联支路**（§我 t40 §6.3 已证 `K76.S1.5` 与 `K110.S1.5` 同在 `BST_F_S1` net、`K76.S1.4` 与 `K110.S1.4` 同在 `BST_S_S1` net）⇒ **不造成冲突**、**不新增假绿**；
- ⇒ **补两者的交集为空、并集安全**；**仅"删除 `K110`"在两种裁定下都不安全**（若 ch18 成立则断链）。
- **副作用如实标注**：并集策略会**多闭**，故 **`--check-extra`（"不得多闭"）不得在本次启用**，否则会对"多闭的那一路"报红；**该限制须写入 payload 注释与 t34 限制清单**。
**⚠️ 同时更正一条既有记账**：**t29 的定性应由"依约保守（可能多闭）"改为"**在 t42 成立时属缺件，在契约字面成立时属合规**"** —— 我已据此更新 `review/t40-…md` §6 的前提注解；**t29 的 `pass` 仍然有效**（它针对的是"是否满足契约字面权威"，该问题与 ch5/ch18 之争**正交**）。

## 5. 对 t42/t44 的其余部分：采纳与不采纳
