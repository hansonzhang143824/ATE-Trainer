1. 第一次打开：先做这 5 步

  1. 从 DSH 宿主进入 ATE Trainer，或打开 /agent-trainer。
  2. 确认页面顶部显示当前项目、候选 revision 和当前模式。
  3. 第一次操作先停留在训练模式，不要一开始就进入发布模式。
  4. 在左侧选择一个 Agent 或工作流；如果页面正在加载，先刷新一次。
  5. 完成一次原生会话或合成业务运行，再根据运行记录决定是否优化。
✓能看到 Agent、工作流、训练模式，以及“打开原生会话”或“创建并打开原生会话”按钮。
✓页面显示的候选 revision 是本次操作使用的版本；保存后它会变化。

2. 系统是什么，架构怎么走

ATE Trainer 是一个训练和发布工作台。它把“定义一个 Agent”“把多个 Agent 排成工作流”“在真实 DSH 子会话中执行”“留下可追溯证据”“冻结并发布”串起来。你在白色工作台做控制，模型和聊天在 DSH 原生窗口里完成。

DSH 宿主提供原生会话、模型和窗口
→
ATE Trainer 页面目标选择、编辑和运行控制
→
候选 revisionAgent、schema、workflow
→
原生 Trainer 会话真实输入和 Trainer 工具
→
运行证据步骤、输入、输出、状态
→
冻结 / 发布工程模式回放
A

Agent

一个独立的执行单元，有名称、任务、输入和输出约束。

W

工作流

按顺序调用多个 Agent，并定义步骤之间传什么数据。

R

候选与发布

候选可以修改；冻结后形成版本；工程模式使用已发布版本。

3. 先认清几个概念

名称用人话解释你在哪里看到
Agent Trainer负责训练和管理 Agent 的 DSH 原生会话预设。原生会话顶部的 preset
Trainer 工作台白色网页控制面板，负责编辑、运行、发布和看记录。/agent-trainer
原生会话真正由 DSH 创建的会话；你在这里输入消息，模型在这里回答。DSH 会话窗口或会话列表
候选 revision当前正在修改的草稿版本。页面标题和保存结果
运行 run某个版本实际跑过一次后的完整记录。运行列表和证据文件
host-default 模型使用当前 DSH 宿主已选中的模型，模型可以是 GLM、DeepSeek 或其他可用模型。原生会话模型选择器

注意 “Trainer 面板里的会话输入框”不是当前目标。正式训练应点击按钮跳进 DSH 原生会话，再在原生窗口输入。

4. 创建一个 Agent

  1. 进入训练模式，选择创建 Agent 的入口。
  2. 填写稳定的 Agent ID，例如 agent-demo-1，名称和任务说明要能让别人看懂。
  3. 定义输入字段和输出字段。比如输入是 question:string，输出是 answer:number。
  4. 写清楚限制：是否只返回 JSON、是否允许解释、失败时怎么返回。
  5. 点击保存候选，确认页面出现新的 revision 或 change set。
  6. 保存后打开原生会话，用一条简单问题验证它确实能回答。

最小示例

Agent ID: agent-demo-1
任务：回答简单算术问题。
输入：{"question":"1+2"}
输出：{"answer":3}
要求：只返回 JSON，不输出额外解释。
✓Agent 出现在当前项目列表中。
✓保存后 candidate revision 有记录。
✓点击原生会话后，DSH 窗口显示 agent-trainer preset。

5. 如何优化 Agent：以 agent-T2 为例

优化的关键是让原生会话实际调用 Trainer 工具保存候选。模型口头说“已经改好”不算完成，必须看到 revision、变更记录和复测结果。

  1. 在训练模式选择 agent-T2。
  2. 点击创建并打开原生会话；如果已经绑定过，就点击打开原生会话。
  3. 确认已经跳到 DSH 原生窗口，并确认 preset 是 agent-trainer。
  4. 在原生输入框发送下面的指令。
  5. 回到 Trainer 页面，检查候选 revision、变更记录和验证状态。
  6. 运行 Agent，确认新的输出是 231。
请读取当前 trainer_context 和 trainer_assets。
把 agent-T2 的执行任务改为：计算 11*21。
请实际调用 trainer_apply_changes 保存候选，
再调用 trainer_validate 校验。不要只口头说明。
保存完成后告诉我新的 revision。

应该看到什么

出现 change set；候选 revision 更新；校验结果为通过；新的运行输出为 {"answer":231}。

如果只得到一段解释

说明模型没有实际调用 Trainer 工具。继续要求它调用 trainer_apply_changes 和 trainer_validate，再回页面看 revision。

6. 如何创建工作流

  1. 训练模式选择新建工作流，给它一个容易识别的名称。
  2. 选择要加入的 Agent，点击加入或添加步骤。
  3. 用上移、下移调整执行顺序，用删除移除不需要的步骤。
  4. 为每一步检查输入和输出绑定：下一步使用的字段必须来自上一步声明的输出。
  5. 保存候选后运行一次，查看每一步是否完成。
步骤 1 · Agent A接收初始输入
→
步骤 2 · Agent B接收 A 的绑定输出
→
步骤 3 · Agent C产生最终结果

工作流的最终输出和某一个中间 Agent 的输出可能不同。看结果时要先确认你问的是“当前 Agent 输出”还是“工作流最终输出”。

7. 如何优化工作流

  1. 先记下当前步骤顺序、每步 Agent ID、输入绑定和输出绑定。
  2. 在原生工作流会话中说明需要怎样调整，例如把顺序改为 agent-T2 → custom-agent-7。
  3. 要求会话调用 trainer_apply_changes 保存，再调用 trainer_validate。
  4. 回到工作台确认 workflow revision 已更新，再运行新版本。
  5. 比较新旧 run 的步骤数、顺序、每步输入、每步输出和最终结果。
  6. 验证通过后再冻结；冻结后的版本交给发布模式审核。

排查顺序

先看步骤顺序，再看 input/output binding，最后看 Agent 自己的任务说明。

通过信号

新 run 使用新 workflow revision，每个步骤都有完成状态，最终输出与预期一致。

8. 如何在原生会话中训练

Agent 和工作流都通过同一种方式训练：从 Trainer 点击按钮创建或打开 DSH 原生会话，然后在 DSH 的真实输入框里聊天。

操作在哪个窗口目的
选择 Agent / 工作流Trainer 白色工作台告诉系统这次要训练谁
创建并打开原生会话Trainer 白色工作台按钮创建绑定关系并跳到 DSH 会话
输入训练指令DSH 原生会话输入框与真实模型沟通和调用 Trainer 工具
保存、运行和发布Trainer 白色工作台产生 revision、run、冻结版本和发布记录

聊天模板：先读事实，再动手

请先读取 trainer_context 和 trainer_assets，告诉我当前绑定目标。
然后按我的要求调用 trainer_apply_changes 保存候选，
调用 trainer_validate 校验，最后告诉我 revision 和校验结果。
不要只给建议，也不要只口头声称已修改。

原生会话使用当前 DSH 宿主默认模型，所以不要求必须是 DeepSeek。实际使用哪个模型，以原生窗口显示的模型为准。

9. 保存、冻结和发布

候选版本可以修改；冻结版本用于审核；发布版本供工程模式回放。发布前一定先完成训练运行和校验。

顺序你要做什么检查什么
1训练模式保存候选revision / change set 已记录
2运行 Agent 或工作流status 为 completed，输出正确
3冻结候选生成不可变 frozen snapshot 和 SHA-256
4进入发布审核候选变为只读，核对运行证据
5发布并激活生成 release 记录和发布哈希
6工程模式回放使用已发布版本产生新的 publish run

发布隔离 训练模式后来又改了候选但没有重新发布时，工程模式仍应使用旧的已发布版本。这是发布隔离的核心验证。

10. 自己点击验证 Agent 和工作流

下面是可以照着执行的验收脚本。每一步都要真的点击按钮、在真实会话里输入内容，并记录页面显示的 run ID。

A. 验证单个 Agent 的原生会话

  1. 打开 ATE Trainer，进入训练模式。
  2. 选择一个当前 Agent，点击创建并打开原生会话。
  3. 在 DSH 原生输入框输入：1+2等于几，把答案写在JSON里。
  4. 确认原生会话返回 JSON，并且 answer 是数字 3。
  5. 回 Trainer 页面运行一次，确认状态为 completed，并能看到输入、输出和 revision。

B. 验证 agent-T2 优化

  1. 选中 agent-T2，打开原生会话。
  2. 输入本页第 5 节的优化指令。
  3. 确认原生会话实际调用了保存和校验工具。
  4. 回页面运行，确认输出变成 231，并且使用了新的 revision。

C. 验证合成业务 BUSINESS_ONLY

  1. 回到 Trainer 训练页面，找到合成业务 BUSINESS_ONLY（23*24+45=597）按钮。
  2. 点击运行，等待页面显示完成。
  3. 打开运行详情，确认步骤输出为 597，最终输出也为 597。
  4. 确认执行模式是 BUSINESS_ONLY，状态是 completed，子会话终止已确认。
  5. 确认 businessGatePassed:false；这表示当前只验证流程连通，不把合成数据当成真实业务结论。

D. 验证工作流编辑

  1. 创建或选择一个工作流，记下原来的步骤顺序。
  2. 添加、删除或上下移动一个步骤。
  3. 保存候选，确认 workflow revision 更新。
  4. 运行工作流，确认每一步都有输入、输出、状态和 handoff。
  5. 再次打开原生工作流会话，要求它读取当前工作流并实际校验。
✓原生 Agent 会话真实返回内容，不是 Trainer 页面伪造的聊天记录。
✓597 运行从按钮触发，Agent、工作流、运行记录和最终输出都能对上。
✓修改候选后 revision 变化，未发布候选不会改变工程回放版本。

11. 到哪里查看验证证据

证据内容
Training_Materials/runs/<runId>/framework-run.json运行模式、revision、步骤输入、输出、状态和 gate。
Training_Materials/framework/control/bindings/<sessionId>.json原生会话绑定到哪个 Agent 或工作流、使用哪个 preset。
Training_Materials/framework/control/requests/agent-trainer/原生会话提出的请求、变更和校验结果。
publish/versions/<releaseId>/冻结和发布后的版本、清单和 SHA-256。
publish/runs/<runId>/framework-run.json工程模式回放的实际记录。
当前验收证据 JSON已完成的点击验证和范围说明。

查看证据时优先核对 runId、revisionId、executionMode、status、finalOutput 和 businessGatePassed。哈希必须是小写 64 位 SHA-256。

12. 常见问题

为什么看不到原生聊天内容？

Trainer 页面只负责控制；聊天内容在 DSH 原生会话窗口。点击“打开原生会话”即可回到绑定窗口。

为什么没有马上看到回复？

先确认当前标签页是 DSH 原生会话，输入框已经发送成功，再看会话状态和模型选择器。

为什么模型不是 DeepSeek？

当前策略是 host-default，使用 DSH 宿主当前选择的可用模型。只要原生会话能执行，就不要求固定模型名称。

为什么结果是 597？

这是合成 BUSINESS_ONLY 验证用的 23*24+45，用于验证流程，不代表真实半导体业务计算。

为什么 businessGatePassed 是 false？

当前范围刻意不执行真实业务门禁。这个字段为 false 是预期结果。

旧八专家在哪里？

它们作为历史资料保留在归档目录，不进入当前 Trainer 的活动列表，也不参与本次验收。

!
判断完成的标准：原生会话能真实对话，Agent 能保存和复测，工作流能编辑和运行，597 合成业务能完成，运行证据可追溯，发布回放不受未发布候选影响。
