## 2. 两段式写码 + 编译节奏（2026-09-13 用户拍板）

### 2.1 两段式：先正确，后归位（归位 = 保留步骤）

- **阶段 1 (正确性)**: 新 TM **全部追加到文件尾部** → `fast_rebuild -Incremental` 编译过 + 门禁过。
- **阶段 2 (归位)**: 按 **TM 编号顺序**把每个 TM 函数块移动到规范位置（**保留步骤**，2026-09-13 用户选 (b)）。**最小移动单位 = 单个 TM 单元**（一个 TM 的完整函数体 + 其 AFX 注释块），不拆行/不半截移动。移动用脚本定位 + 字节模式替换 (DLP)，**移动后必须再增量编译一次**。
- 函数定义顺序不影响链接，归位是纯工程性重排，安全；先正确后归位，两段互相解耦。
- **为什么要"归位后再编译一次"**（用户 2026-09-13 确认的原始理由，务必保留）：
  代码**起先是按"不考虑贴在程序哪里"写的、统一追加在尾部**，最后才**组装**进程序 → **这次编译就是检查组装有没有出错**。
- **零移动例外**: 若本批追加后文件**已按 TM 编号递增**（无逆序，实测常见——各批次多按递增顺序写）→ 归位 = 零移动，**阶段1 与阶段2 的编译可合一**（省一次），但收尾须注明「本批零移动」。

### 2.2 编译节奏（2026-09-13 用户拍板：**默认全部写完编一次**）

> ⚠ **先澄清一个易误读点**：**per-TM 那一步是「冒烟」，不是编译** —— `verify_single_fn.py` 秒级、无需编译。

| 步骤 | 频率 |
|---|---|
| **冒烟** `verify_single_fn.py` | **每 TM 一次**（FAIL **停留当前 TM**，不得进下一个） |
| **B-001 代表函数先行** | **每批 1 次**：先插 1 个代表函数 → 编译 + 门禁全绿 → 再批量放量 |
| **编译** | **全部写完编一次**（阶段1）→ **归位后再一次**（阶段2，查组装） |

**为什么"末尾一次"是安全的 —— 三条兜底，缺一不可**：

1. **per-TM 冒烟**挡占位符残留 / 分号在注释后 / 花括号 / CRLF / 六步结构 / 寄存器解锁顺序；
2. **B-001 代表函数先行**挡**模板与数据 dict 的系统性错误**（写错一次错一批）—— 这正是"中途多编译"最想防的，**已被它覆盖**；
3. **MSVC 报错带行号**，而新增 TM 是**连续追加在文件尾部** → 大批次里也能一眼定位，**不以"批次规模"为代价**。

**实测支撑**：历史大批次本来就是"末尾一次"且都过了 —— **TM113~215（37 个）** 与 **TM403~425（15 个）** 均 **0 errors / 0 warnings**。

**可选保险（默认不启用）**：仅当你**观察到某批出现系统性出错**（同一类错在多处复现）时，才临时加中点编译；**不要在正常批次上常态化**。

- **成本实测（2026-09-13 现场量，非估算）**：

  | 项 | 实测 |
  |---|---|
  | `fast_rebuild -Incremental` **真实重编 test.cpp + 链接** | **3.2~4.4s**（3 轮）；无改动 no-op **0.6s** |
  | 冷启动首次编译（新会话第一次） | ~25s（一次性；同操作随后只要 ~4s） |
  | VS 保存的 COM 探测（VS 未运行） | **0.02s** ← 可忽略 |
  | 门禁脚本链 12 个合计 | **3.59s**（单个 0.19~0.67s）← 可忽略 |
  | 完整 `Build` vs `/t:ClCompile` | 4.1s vs 3.6s → **只省 0.5s**，且**跳过链接检查**（参数名不符/符号未定义这类错只在链接期暴露）→ **不采用** |

- **成本大头是「轮数」不是「秒数」**：每次编译在会话里 = **一次完整的模型往返**（模型要把整段累积上下文重新处理一遍）。所以压编译频率的真实收益 = **少几轮上下文重算**，机器时间只省几秒。
  → **同理：合并工具调用（12 次门禁 → 1 次）比调编译频率更划算**（前者省 11 轮，后者省 3 轮）。

### 4.1 读证（receipt 必须交的证据）— 2026-09-13 用户拍板 B

> 材料门原先是**存在性门**（参数类型一登记就 PASS，根本不比对 receipt 声明了什么）——**TM607-609 的根因正是"材料存在却未读取"**。升级为**被用性门**后，生成前写 receipt 时必须同时给出：

```json
"TMxxx": {
  "param_type": "UVLO",
  "materials": ["L1-chip/UVLO.md", "L3-method/UVLO.md", "L4-Golden-code/UVLO.cpp"],
  "goldenSha256": {"L4-Golden-code/UVLO.cpp": "<sha256>"},   // ① 按内容读过(可与磁盘复核)
  "structures": {                                            // ② 四类结构已提取(非空)
    "dut_body": "...", "fpvi_short": "...",
    "paired_staircase": "...", "measure_essence": "..."
  }
}
```

- **①** 哈希冻结 = 证明按内容处理过、且可与磁盘复核（不符 → FAIL，防"抄错文件/事后被改"）。
- **②** 四类结构非空 = 证明**真的做了 §5 的提取**（只声明文件不提取结构 = 材料存在却没用上 → FAIL）。
- 门禁：`python verify_material_receipt.py`（生成前，Step4 ①）；自检 `--audit-rules`（必读材料路径存在 + 与索引参数类型一致）。
- 既有收据（早于本机制）用 `readProofWaived: "<理由>"` 显式豁免 → 只 WARN 不 FAIL，**禁止追溯伪造读证**。

## 5. 黄金案例 = 关键特殊结构参考, 非继电器/PIN 字典（2026-08-26 用户拍板）

用 golden 前先提取它的**关键特殊结构** (抓关键点推断, 不机械模仿):
① **被测件本体结构**: 被测元件两端各连哪个节点 (如 HS 上管 = PMID↔SW);
② **大电流路径 → FPVI 短接**: 被测路径过大电流 → FPVI 把两端"短接" (FPVI[高]→一端、FPVI[低]→另一端);
③ **配对/台阶结构**: 哪些节点成对、压差必须始终满足台阶上下电 (如 **BST−SW 一对**: BST≥SW 且 BST−SW≤5V 每步都要保证; 自举电容 Cap_SW_BST 是配对一部分);
④ **测试方法本质 (测量值怎么来)**: 测的是什么量、怎么得到测量值 (如 ZCD **电流阈值** → rampi_capv 电流 ramp + 抓其他 PIN 翻转, **翻转点电流值 = ZCD 值**, 单阈值无迟滞无 Hys)。

- **PIN 是一般性角色的实例, 不是名称迁移**: 上面的 PMID↔SW、BST−SW 只是"角色"在本项目的实例——SW↔PGND = **被测 MOSFET 的两个端点**、BST−SW = **一组台阶电压对的两个端点**; 到下一项目这两个角色可映射成 **SW1↔VBUS**、**BST2−CFH2**, 写法不变 (FPVI 短接 MOSFET 两端 + 台阶对压差每步满足)。golden 的 PIN 名零可迁移性, 只提取"角色"。
- 具体继电器/PIN 按**角色**从当前项目权威源解析 (meta capAuthority → SCH-Connect-Map 稳压/通路行 → gen_path_defines 产物), **绝不抄 golden 的 Kxx** (golden 的 Kxx 只表示"这里需要一个某角色的继电器")。
- **不知道提取什么作为关键信息 → 向用户提问**, 不要机械套用。

## 6. 材料三档 + 按组加载 + 隔离（2026-09-13 用户拍板：降上下文）

> 原则：**先吃「通用方法」，不够再按分类进案例；原文一律按需**。
> 实测体量差两个数量级（OTP 家族：Tier1+Tier2 ≈ **14KB**，Tier3 全量 ≈ **357KB**）。

### 6.1 三档定义（`MATERIAL_REQUIREMENTS` 按此建模）

| 档 | 是什么 | 落点 | 加载时机 |
|---|---|---|---|
| **Tier1 通用方法**（公共流程） | 该族的**一般性方法**：流程骨架 + 家族通用机制 + 代码框架要点 | `L1-chip/<族>.md` + `L3-method/<族>.md` | **批次级读一次**（小件，父会话可持有） |
| **Tier2 类型层注解** | 该族的**分支/项目变体**要点（协议差异、判据命中、卫生问题） | `L4-Golden-code/<案例>.md`（**必读**，按 `branch` 过滤） | **组级** |
| **Tier3 原文** | 真实工程代码 | `L4-Golden-code/<案例>.cpp/.txt`（**按需**：登记后校验存在性 + 读证） | **组级 · 子会话内**，读完即弃 |

**判定顺序（2026-09-13 用户拍板：Tier1 是黄金案例使用的第一步，且必须做）**：

```
① 读 Tier1 通用方法（L1-chip + L3-method）              ← 必做第一步，不是可选
      ↓
② 判「Tier1 够不够写完这个程序」
   ├─ 够   → 收据记 tier1=sufficient
   │         **不加载任何案例**（此时若声明 Tier3 原文 → 门禁判「矛盾」直接 FAIL）
   └─ 不够 → 收据记 tier1=insufficient
              ↓ 先 Tier2 类型层（.md，按 branch 过滤，**必读**）
                 ↓ 仍不够 → Tier3 原文（**按需**，只读 branch 匹配的 1 份，子会话内读完即弃）
```

- **`tier1` 必须落收据**（有 Tier3 阶梯的类型即强制）——否则「只读 Tier1 就写码」与「判过 Tier1 够用」无法区分，而**后者才是允许跳过案例的依据**。门禁会校验二者不矛盾。
- `OTP·MTP` 是首个按此建模的类型：`branch` ∈ {`OTP` → 案例1~3, `MTP` → 案例4~5}；5 份 `.txt` 全进 `code_ondemand` 菜单，**不再强制全读**。
- ⚠ **目前只有 9 类参数有 Tier1**（L1-chip + L3-method）；`VBG` / `BUCK HS Gain` / `VC_CLAMP_LOW` / `VAC GD present` 四类的 `chip`/`method` **待归档** → 这几类「Tier1 优先」无处落地，等于直接吃 golden。补 Tier1 是这几类降上下文的唯一途径。

### 6.2 分组键（决定「加载一次」的粒度）

```
组 = (param_type, 测试条件指纹)
测试条件指纹 = 拓扑(被测件两端/配对结构) + 观测 PIN + 量程档 + 寄存器序列骨架
```

同一组的 N 个 TM **共享一次 golden 加载**（8 个同族 Toggle → 1 次）；**条件不同即不同组**（如 Current Threshold 的 LS/BUCK 与 HS/BOOST 必须分两组）。

### 6.3 隔离（「移出上下文」的真实手段）

> ⚠ 本 harness **没有**「从上下文删除已读内容」的能力（上下文即对话历史，读进来越往后每轮都重算）——所以只能**不让它进来**：

1. **每组一个 subagent**：子会话读 Tier2/Tier3 → 写该组全部 TM 的 code → **只回交**「代码 + 组级读证(四类结构 + goldenSha256) + 组内冒烟结果」。**父会话从不持有 golden。**
2. **指针化落盘**：四类结构写进收据，后续只引用指针，不重读。
3. **组内一次性**：同组共享 1 次加载。

- 收益：父会话上下文 ≈ **O(组数)**，而非 O(TM 数 × 每 TM 载入量)（后者是 O(N²) 的增长源）。
- 代价：spawn/协调开销 → **批量 ≥5 个 TM 才划算；1~2 个 TM 直接按索引读一份写就完了，别套这套。**

### 6.4 读证落在「组」（不是 TM）

每组交一次：`goldenSha256`（声明的每个 L4 文件，与磁盘复核）+ `structures` 四类关键特殊结构（§5）。
—— 既证明「这组确实按 golden 写了」，又不随 TM 数膨胀（堵 §4.1 的「材料存在却没读」，成本却摊薄到组）。
